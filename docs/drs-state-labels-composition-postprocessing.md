# DRS State Labels: Composition vs. Post-Processing

This note records an important difference between the DRS shown after semantic composition and the DRS generated by the `Generate PCDRS` button.

## Composition output

The semantic-composition path keeps the resolved LFGxDRT DRS object in memory. During merge resolution, LFGxDRT allocates state labels and retains merge provenance (`mergeParents`). The SVG renderer receives that object directly, so it can display both ordinary DRS state labels and labels associated with merge boundaries.

Relevant backend code:

- `../GlueSemWorkbench_v2/src/main/java/webservice/rest/GswbController.java`
- `../LFGxDRT/src/main/java/de/ukon/lfgxdrt/drs_elements/DRS.java`
- `../LFGxDRT/src/main/java/de/ukon/lfgxdrt/drs_elements/DrsMerge.java`

## Post-processing output

The client-side `Generate PCDRS` flow does not send the original in-memory DRS. It sends `selected.semantic` from `src/app/glue-interface/glue-interface.component.ts` to `/generate_pcdrs`.

The current backend creates that semantic payload with the default `DRS.toString()`. That method delegates to `toString(false)`, so state-label prefixes are omitted. The PCDRS endpoint then reparses the flattened string and adds anaphora mappings.

This reparsing step cannot restore the original `mergeParents` metadata or the original state-label allocation. Consequently, post-processing output should not be assumed to have the same state labels or merge-boundary labels as the composition output.

Relevant handoff points:

- Client request: `src/app/glue-interface/glue-interface.component.ts`, `generatePcdrs()`
- Client display: `src/app/sem-vis/sem-vis.component.ts`, SVG solution handling
- Backend request parsing: `../GlueSemWorkbench_v2/src/main/java/webservice/rest/GswbController.java`, `/generate_pcdrs`
- DRS serialization: `../LFGxDRT/src/main/java/de/ukon/lfgxdrt/drs_elements/DRS.java`, `toString()` and `toString(boolean)`

## What to look out for

- Do not compare the composition SVG with the PCDRS `semantic` string and assume they represent the same level of information.
- A label-free semantic string may still produce a newly allocated simple DRS label after parsing, but it cannot reproduce merge-boundary labels or the original label numbering.
- If state labels become important for post-processing, preserve structured DRS/merge metadata across the API boundary instead of relying only on `toString()` output.
- If only textual labels are needed, check whether the producer should use `toString(true)`. This alone does not preserve `mergeParents`.

This is currently a documented follow-up concern, not an urgent change requirement.
